1 · What this project is

SFx Lite is the backend API for a lightweight fintech app (USDC wallets, deposits, transfers, a ledger, KYC and an AI support chat). This repository is the boilerplate: the shared foundation — configuration, security, rate limiting, logging, error handling, database wiring and health checks — on top of which each squad ships feature modules.

Nothing business-specific is implemented yet. The point of the boilerplate is that when you add a feature you only write the feature; everything cross-cutting (validation, auth hooks, response shape, error shape, throttling) already works for free.

3 · Quick start

Node 20+ and a reachable PostgreSQL database. That's it.

Steps

# 1. install dependencies
npm install

# 2. start the dev server (watch mode)
npm run dev
#    → .env is created automatically from .env.example on first run
#    → API:     http://localhost:4000/api/v1
#    → Swagger: http://localhost:4000/docs

The app validates its config on boot. If a required variable is missing it refuses to start and tells you exactly which one — this is intentional (fail fast). See the next section.

4 · Environment & the auto-.env bootstrap

Configuration is driven entirely by environment variables. There are three files involved:

FileRole
.env.exampleCommitted template with every variable and a safe default. The source of truth for "what config exists".
.envYour local, git-ignored copy. Created automatically (see below). Put real secrets here.
scripts/ensure-env.jsCopies .env.example → .env if .env is missing, so a fresh clone boots with zero manual setup. Skipped in production, where platform env vars are the source of truth.

How the auto-bootstrap is wired

ensure-env.js runs through npm pre-hooks — npm automatically runs a pre<script> before <script>. In package.json:

"predev":       "node scripts/ensure-env.js",
"dev":          "nest start --watch",
"prestart":     "node scripts/ensure-env.js",
"start":        "nest start",
"prestart:dev": "node scripts/ensure-env.js",
"start:dev":    "nest start --watch",
"prebuild":     "node scripts/ensure-env.js",
"build":        "nest build"

So whichever way you launch (npm run dev, start, start:dev, or build) the .env is guaranteed to exist first.

Fixed: "Config validation error … DATABASE_URL is required" on first run. Earlier, ensure-env.js existed but was never called — there were no pre* hooks, so .env was never generated and the app crashed on boot with missing DATABASE_URL / JWT_ACCESS_SECRET / JWT_REFRESH_SECRET. The pre-hooks above now wire it in, and a .env has been generated for you. If you ever hit this again, just run node scripts/ensure-env.js (or copy .env.example to .env) and set a real DATABASE_URL.

Validation (fail-fast) — src/config/env.validation.ts

On boot, a Joi schema checks the environment. Required values that must be present or the app won't start:

VariableRule
DATABASE_URLRequired. Must be a postgres:// / postgresql:// URI.
JWT_ACCESS_SECRETRequired. Min 8 chars.
JWT_REFRESH_SECRETRequired. Min 8 chars.
PORT, API_PREFIX, throttle vars…Optional — sensible defaults applied.

Later-stage secrets (chain RPC, Cloudinary, Anthropic) are intentionally not required at boot; the module that consumes them enforces them when it needs them.

Reading config in code — never touch process.env directly

src/config/configuration.ts maps raw env vars into a typed, namespaced object. Inject ConfigService and read by dotted key:

constructor(private readonly config: ConfigService) {}
// ...
const port = this.config.get<number>('port');
const dbUrl = this.config.get<string>('database.url');
const ttl = this.config.get<number>('throttle.ttlSeconds');

6 · The request lifecycle

Knowing the order things run in explains where each file fits. For an incoming request:

  • Middleware — RequestIdMiddleware attaches an x-request-id, then HttpLoggerMiddleware starts timing. (Wired in app.module.ts → configure().)
  • Guards — AppThrottlerGuard enforces the rate-limit budget (per-user if authenticated, else per-IP). @Public()/@SkipThrottle() opt routes out.
  • Pipes — the global ValidationPipe validates & transforms the body against the route's DTO. Unknown fields are stripped and rejected.
  • Controller — the matched route method runs. It does almost nothing but call a service.
  • Service — business logic executes (DB queries, token work, external calls) and returns a plain object.
  • Interceptors — TransformResponseInterceptor wraps the return value in the standard envelope; TimeoutInterceptor aborts anything over 30s.
  • Exception filter — if anything threw, AllExceptionsFilter converts it into the standard error shape (and logs 5xx with the request id).

Every success looks like this

{ "success": true, "data": { ... }, "timestamp": "2026-07-13T..." }

Every error looks like this

{ "success": false, "statusCode": 404, "error": "NotFoundException",
  "message": "User not found", "path": "/api/v1/users/42",
  "requestId": "…", "timestamp": "2026-07-13T..." }

Because the envelope and error shape are global, your feature code just returns data or throws a Nest exception — the wrapping is automatic.

7 · The module / controller / service / DTO pattern

A feature is made of four kinds of files. Here's what each one is responsible for, using the real health module as the example.

Module — wires the pieces together

Declares what the feature imports, which controllers expose routes, and which providers (services) are injectable. Registering the module in app.module.ts is what activates its routes.

@Module({
  imports: [TerminusModule],
  controllers: [HealthController],
  providers: [HealthService],
})
export class HealthModule {}

Controller — the HTTP surface

Declares routes and their Swagger metadata, and delegates all logic to the service. @Controller('health') + the global /api/v1 prefix means these resolve to /api/v1/health.

@ApiTags('health')
@Controller('health')
export class HealthController {
  constructor(private readonly healthService: HealthService) {}

  @Get()            // → GET /api/v1/health
  @Public()
  check() {
    return this.healthService.check();
  }

  @Get('live')      // → GET /api/v1/health/live
  @Public()
  live() {
    return this.healthService.liveness();
  }
}

Service — the business logic

Where the real work lives. Injected into the controller. It talks to the DB, other services and indicators, and returns plain objects (the interceptor wraps them).

@Injectable()
export class HealthService {
  constructor(
    private readonly health: HealthCheckService,
    private readonly db: TypeOrmHealthIndicator,
    private readonly memory: MemoryHealthIndicator,
    private readonly config: ConfigService,
  ) {}

  check() {
    return this.health.check([
      () => this.db.pingCheck('postgres', { timeout: 3000 }),
      () => this.memory.checkHeap('memory_heap', 512 * 1024 * 1024),
    ]);
  }

  liveness() {
    return { status: 'ok', uptimeSeconds: Math.round(process.uptime()) };
  }
}

DTO — request shape & validation

A DTO is a class describing a request body plus its validation rules. The global ValidationPipe enforces the decorators before the controller runs, so services can trust their input. (From the auth skeleton:)

export class LoginDto {
  @ApiProperty({ example: 'ada@example.com' })
  @IsEmail()
  email!: string;

  @ApiProperty({ example: 'super-secret' })
  @IsString()
  @MinLength(8)
  password!: string;
}
Rule of thumb Controllers are thin (routes only). Services are where logic lives. DTOs guard the input. Modules glue them together. If you're writing an if in a controller, it probably belongs in a service.

8 · API documentation (Swagger)

Interactive API docs are served at http://localhost:4000/docs in development (disabled in production). They're generated from your code — you never hand-write or maintain a schema file. Two halves work together:

The setup half — src/config/swagger.config.ts

One central setupSwagger(app) function builds the OpenAPI document (global title, version, bearer-auth) and mounts the UI at /docs. main.ts just calls it:

// src/config/swagger.config.ts
export function setupSwagger(app: INestApplication) {
  const config = new DocumentBuilder()
    .setTitle('SFx Lite API')
    .setDescription('SFx Lite — Intern Build Program')
    .setVersion('0.1.0')
    .addBearerAuth()
    .build();

  const document = SwaggerModule.createDocument(app, config);
  SwaggerModule.setup('docs', app, document);
  return document;   // returned so you can optionally write it to disk
}

// src/main.ts
if (!isProd) {
  setupSwagger(app);
}

The content half — decorators next to each route

createDocument() scans every controller and DTO and pulls in their decorators. So each endpoint is documented where it's defined, and the docs can't drift from the code:

@ApiTags('auth')                 // groups routes under an "auth" heading
@Controller('auth')
export class AuthController {
  @Post('login')
  @ApiOperation({ summary: 'Exchange credentials for access + refresh tokens' })
  @ApiResponse({ status: 200, description: 'Tokens issued' })
  @ApiResponse({ status: 401, description: 'Invalid credentials' })
  login(@Body() dto: LoginDto) { ... }
}

// DTOs describe request bodies:
export class LoginDto {
  @ApiProperty({ example: 'ada@example.com' })
  @IsEmail() email!: string;
}
DecoratorPut it onDoes
@ApiTags('x')ControllerGroups its routes under one heading in /docs.
@ApiOperation({ summary })Route methodOne-line description of the endpoint.
@ApiResponse({ status, description })Route methodDocuments each possible response.
@ApiProperty({ example })DTO fieldDescribes a request/response field + example.
@ApiBearerAuth()Route/controllerMarks a route as needing the bearer token.
Why code-first, not a hand-written swagger.json Decorators live next to the code they describe, so the docs update the instant a route changes. A hand-maintained schema drifts out of sync the moment someone forgets to edit it. If the frontend needs a static spec for client codegen, generate it — add writeFileSync('./openapi.json', JSON.stringify(setupSwagger(app), null, 2)) — never write it by hand.

9 · Caching (cross-module, graceful)

A single CacheService is available to every module, backed by Redis when it's there and an in-memory store when it isn't. It lives in src/common/cache/ and is registered as a @Global() module, so you inject it anywhere without importing anything.

Cache never blocks development or deployment. If REDIS_URL is unset, or Redis is unreachable, or the ioredis package isn't even installed, the app falls back to a bounded in-memory cache and keeps running — locally, in staging, and in production. Every cache call is wrapped so a cache failure degrades to a miss, never an error. No Docker required.

Two ways to use it

1 — Cache a GET response declaratively with @Cacheable(). Only routes that opt in are cached (so writes never are), and keys are per-user by default so data can't leak between users:

import { Cacheable } from '../../common/cache/cache.decorators';

@Get('rates')
@Cacheable(30)                 // cache this response for 30 seconds
getRates() {
  return this.fxService.latest();
}

2 — Cache anything inside a service with wrap() (read-through) or the raw get/set/del:

constructor(private readonly cache: CacheService) {}

async latest() {
  // returns cached value, or runs the fn, caches it, and returns it
  return this.cache.wrap('fx:usd-ngn', () => this.fetchFromProvider(), 30);
}

// or manually:
await this.cache.set('user:42:profile', profile, 120);
const p = await this.cache.get<Profile>('user:42:profile');
await this.cache.del('user:42:profile');   // invalidate after an update

Turning on the shared (Redis) cache

Optional, and only useful once you run more than one instance (so they share a cache). Two steps:

npm i ioredis
# then in .env:
REDIS_URL=redis://localhost:6379     # or your managed Redis / rediss:// URL

On boot the log tells you which backend is live — Redis cache connected. or using in-memory cache. Config lives under the cache namespace (CACHE_TTL_SECONDS, CACHE_MAX_ITEMS) in configuration.ts.

FileRole
common/cache/cache.service.tsThe cache API: get/set/del/wrap, Redis-or-memory, never throws.
common/cache/cache.module.ts@Global() module exposing CacheService everywhere.
common/cache/cache.decorators.ts@Cacheable(ttl?) and @CacheKey().
common/cache/response-cache.interceptor.tsCaches @Cacheable GET routes; registered globally in app.module.ts.
Invalidate on write. The response cache only auto-expires by TTL. After a mutation that changes cached data, call cache.del(key) (or use short TTLs) so users don't see stale results. Never cache authenticated, user-specific data under a shared key.

10 · How to add a new module (step by step)

Say you're adding a wallets feature. Do this:

1. Scaffold (or copy the health folder)

# Nest CLI generates the trio for you:
npx nest g module  modules/wallets
npx nest g controller modules/wallets --no-spec
npx nest g service  modules/wallets --no-spec

# or copy src/modules/health and rename.

2. Add DTOs for any request bodies

// src/modules/wallets/dto/create-wallet.dto.ts
export class CreateWalletDto {
  @ApiProperty() @IsString() label!: string;
}

3. (If it owns data) add an entity + register it

// src/modules/wallets/entities/wallet.entity.ts
@Entity('wallets')
export class Wallet {
  @PrimaryGeneratedColumn('uuid') id!: string;
  @Column({ type: 'numeric', precision: 18, scale: 6 }) balance!: string; // money = numeric, never float
}

// in wallets.module.ts:
imports: [TypeOrmModule.forFeature([Wallet])]
Money is always numeric(18,6), never a float. Ledger rows are append-only; balance changes happen inside DB transactions with row locks. Never use float/double for currency.

4. Write the controller (routes) and service (logic)

Follow the health example above — controller delegates, service does the work.

5. Register the module in app.module.ts

import { WalletsModule } from './modules/wallets/wallets.module';

@Module({
  imports: [ /* …existing… */ WalletsModule ],
})

That's it — the routes now appear under /api/v1/wallets and in Swagger, with validation, throttling, the response envelope and error handling already applied.

6. Generate a migration if the schema changed

npm run migration:generate -- src/database/migrations/AddWallets
npm run migration:run

11 · Database & migrations

There are two TypeORM setups on purpose:

FileUsed byNotes
database/database.module.tsThe running appautoLoadEntities: true, synchronize: false, migrationsRun: false. Never auto-alters your schema.
database/data-source.tsThe TypeORM CLIPoints at src/**/*.entity.ts and the migrations folder for generate/run/revert.

Migration commands

npm run migration:generate -- src/database/migrations/<Name>   # diff entities → new migration
npm run migration:run                                          # apply pending migrations
npm run migration:revert                                       # roll back the last one
Schema changes ship as migrations only. synchronize is permanently false. Generate a migration, review it, commit it. This is a fintech-grade rule — never let the app silently mutate production tables.

12 · Data model — entities & core schema

The starting schema is expressed as TypeORM entities (one <name>.entity.ts per table) under each domain folder in src/modules/. These are the source of truth; run npm run migration:generate to turn them into the SQL that actually creates the tables. The backend team refines these in Week 1.

Entities define the schema; migrations apply it. Because synchronize is off, creating an entity file does not touch the database. The migration CLI (data-source.ts, glob src/**/*.entity.ts) reads every entity and generates a migration. Review it, commit it, and everyone runs npm run migration:run once against the shared database.

Two things to finish by hand in the first migration. Money is always numeric(18,6) (never float), and the ledger is append-only. pgvector: doc_chunks.embedding is declared as text so migrations generate cleanly.
